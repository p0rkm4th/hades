## Findings that change current assumptions

### Open WebUI 0.11.4 native Channels convergence

- Requeried the [official 0.11.4 release](https://github.com/open-webui/open-webui/releases/tag/v0.11.4), which remains the latest release shown by the upstream release page. Upstream notes native channel streaming and tool support.
- The raw immutable 0.11.4 base image (`sha256:332438e…`) passed `scripts/test-open-webui-channels-fixture.sh` and `scripts/test-open-webui-channel-model-fixture.sh`: authenticated/private channel boundaries held; a synthetic model mention reached the OpenAI-compatible backend and its streamed response persisted. This is a direct native-upstream control. The base source still has the old `await CHAT_COMPLETION_HANDLER(...)` expression, but runtime behavior passes without the HADES body-drain patch.
- Added `HADES_OPEN_WEBUI_APPLY_CHANNEL_COMPAT` to the local artifact build path. It defaults to `true`, preserving the tracked 0.11.1 behavior. An earlier continuation incorrectly called image `sha256:5135da5a53c99cbfd25e1d6f94ddad3da50b1f00f7527c251b35baa514ec81b3` a 0.11.4 candidate; image labels and `/api/version` show it is based on 0.11.1, so its full acceptance run does not qualify 0.11.4. Rebuilt the correct candidate from pinned 0.11.4 base `sha256:332438e…` with the Channels shim disabled; image `sha256:17f53d42e4d9e623c5bbdb29ee8ee699f4ae6dd0a4a9f3d913593fa97539ac4b` reports version 0.11.4/revision `8bd8b4f…` and passes `scripts/test-open-webui-candidate.sh`: private-chat persistence/isolation, channel membership/admin boundaries, anonymous denial, and streamed channel persistence. No production pin or deployment changed.
- This qualifies removal of the Channels response-consumption shim **for the correctly based 0.11.4 candidate only**. The 0.11.1 production base still uses the compatibility patch. Other HADES Open WebUI patches remain; each needs its own native-upstream/runtime proof. Candidate DB work so far used empty synthetic SQLite only; populated migration, LDAP/group mapping, Hermes route, file upload, theme/browser-cache and direct owner acceptance are still open. Native terminal access remains disabled.
- Rebuilt the tracked 0.11.1 base with the build-script default (channel compatibility enabled). Candidate image `sha256:3730256dc7377450181affe42e1cf3c6df26549d5d61deb95ff24851b16eae77` passed the same full synthetic acceptance suite, and image inspection confirmed the response-drain code was installed. This verifies the build option default preserves the currently pinned path.
- Shim inventory follow-up: the 0.11.4 raw frontend still contains the exact `let s=t.value;if(s.length<5)` splitter patched by `streaming_compat.py`; the HADES candidate has the string-type guard, so retain pending a reproducing source event that fails without it. The stream-disconnect wrapper, finance/receipt upload adapters, and task-notification endpoint still need separate native capability/runtime audits; no removal inferred from the Channels result.

- Open WebUI 0.11.4 includes upstream auth/access fixes, skill discovery and terminal workflow improvements worth evaluating. It also adds model-visible terminal skills and task execution surfaces; feature availability is not authority approval. Staging proved an empty-database 0.11.1→0.11.4 startup path, not populated data migration or authenticated HADES UX. The official release identifies performance gains in long-conversation streaming and chat persistence.
- Hermes 0.21.5 has native tool search, MCP, context/session handling, worktrees, subagents and computer-use to compare with the seven overlay rows. Its Hindsight provider import path moved to the plugin catalog; the campaign fallback now loads the latest catalog plugin and the focused memory path passes. Three matched CLI greeting pairs found HADES ordinary-turn suppression removed 33 schemas / 43 KB and reduced input from 14,952 to 732 tokens. User-visible TTFC in one streamed pair was 24.0 s HADES / 37.4 s PLAIN; both miss 2 s, and order variance prevents a stable latency conclusion. The isolated profile had no HADES MCP catalog, so this does not qualify action-capability activation. Gateway startup and remaining overlay responsibilities are still open. Native Hindsight has async turn retain and background prefetch, while per-turn memory tools and subject-scope isolation still need HADES-specific proof. The HADES subject-scope resolver and completion-only-model tool isolation remain hard security contracts.
- Hermes-native empty toolsets were tested on CLI and the OpenAI-compatible API gateway. CLI `platform_toolsets.cli: []` sent zero schemas with a 728-token prompt; first model content was 13.10 s and process wall 14.60 s. The loopback-only .21.5 API gateway with `platform_toolsets.api_server: []` reported zero enabled toolsets at `/v1/toolsets`, sent zero schemas with a 714-token prompt, and returned an ordinary greeting in 24.06 s (first model content 22.85 s). A matched follow-up request on that same gateway/model/runtime/hardware/prompt/toolset set, adding only `model_options.reasoning.enabled: false`, reduced first model content to 0.663 s, model request to 2.556 s, and client wall to 3.085 s; output was 54 completion tokens vs 731 in the preceding default-reasoning run. This is strong evidence that default reasoning dominates that greeting latency; it is one synthetic pair, and answer quality plus behavior across the realistic subset still need comparison. The upstream API handler accepts per-request reasoning config. Its toolsets remain static profile configuration, so this does not replace HADES turn-level capability selection. Both candidate gateway runs were loopback-only, used a synthetic API key and no HADES overlay. The Hermes home path caused a nonfatal Unix socket path-length warning during shutdown.
- A one-pass reasoning-mode subset using three sanitized owner-corpus cases (greeting, arithmetic, explanation plus “Why?”) found correct answers in both modes. Reasoning-disabled wall times: 0.99s greeting, 2.99s arithmetic, 8.15s explanation, 2.80s follow-up. Default mode: 50.25s on the first greeting after isolated gateway startup, 3.75s arithmetic, 16.12s explanation, 23.85s follow-up. The first greeting includes initialization and is not comparable as a warm-turn measurement. Reasoning-disabled mode answered “Why?” directly and correctly; its initial explanation was accurate but added an unrequested code sample. Default reasoning also over-expanded the follow-up. This supports a bounded fast-chat experiment, not a global default change: repeat warm matched turns, assess long explanations/coding/research/action, and qualify the HADES API path. Full responses and limitations are in [`plain-stack-reasoning-mode-subset-v1.json`](../benchmarks/plain-stack-reasoning-mode-subset-v1.json). No owner preference was collected.
- The Hermes .21.5 API path with the HADES overlay loaded also accepted explicit `model_options.reasoning.enabled` values for a synthetic owner session. With no configured MCP tools, HADES logged owner scope and cleared zero inherited schemas. A greeting returned under both `false` (2.73s client wall, 11 generated tokens) and `true` (5.74s, 190 generated tokens); the overlay source does not mutate `reasoning_config`. This proves option pass-through and the ordinary API route only; tool actions, household scope, memory, production authentication, and Open WebUI request formation remain untested. See [`hades-overlay-reasoning-option-passthrough-v1.json`](../benchmarks/hades-overlay-reasoning-option-passthrough-v1.json).
- A matched synthetic workspace read exposed a P1 HADES tax. Plain Hermes with its native `file` toolset and an explicitly configured temporary workspace called `read_file` and returned the fixture token `ORCHID-9472`. Under the HADES overlay, the same profile enabled `file`, but the overlay cleared all four inherited tools; with zero schemas and zero tool calls, the model invented a different token and claimed it had read the file. Do not qualify chat-to-workspace or trust a text-only result as a file read. HADES needs owner-scoped workspace capability activation tied to a configured workspace, plus a no-tool-result guard. The precise paired trace is in [`hades-overlay-workspace-read-probe-v1.json`](../benchmarks/hades-overlay-workspace-read-probe-v1.json). No file outside the synthetic fixture was read or modified.
- Follow-up source audit of Hermes 0.21.5 confirms that `terminal.cwd` is a working directory, not a file boundary: file operations use the selected terminal backend and accept paths outside that directory. Hermes' Docker backend can mount an explicit host workspace at `/workspace`, and its task/session override path contains per-session mount selection when Docker isolation is enabled. However, the HADES OpenAI API agent construction does not pass a per-request workspace/CWD, and the Docker backend's documented default image is not pinned by HADES. Neither supported Hermes configuration nor an installed sandbox image was available in this candidate profile. Local Docker image inspection found no Hermes sandbox/default image; no image was pulled or started for this audit. **Decision: keep workspace tools disabled; next implementation slice must bind a trusted HADES owner session to one explicit workspace and a pinned isolated image, then prove the mount boundary and truthful no-tool behavior before enabling tools.**
- Workspace escalation repair was implemented as an opt-in HADES API turn adapter and exercised against the Hermes 0.21.5 candidate. Its private subject workspace is under `HERMES_HOME/workspaces/<subject>`; the active chat/task ID selects Hermes' per-session container, while the authenticated HADES subject selects the only host directory mounted at `/workspace`. The adapter exposes exactly `read_file`, `search_files`, `write_file`, `patch`, and `terminal`, disables network and environment forwarding, suppresses streamed model text until tool results return, and replaces a workspace answer when no successful workspace tool response exists. Synthetic runtime checks pass for owner read, distinct owner mounts, household denial, rootful-Docker denial, no-tool fabricated-answer suppression, and restoration of the empty tool catalog on the following greeting. The test used the official upstream default `nikolaik/python-nodejs:python3.11-nodejs20` amd64 manifest digest `sha256:6ed4d9fb74dc6c7a5caa9120d8d3c507dbf97fb112b7b09d0d9f7d71f1ce919d`; the Hermes file and terminal tools actually read/write within a temporary mount, with a sibling host secret invisible. **This does not qualify deployment activation:** the local user belongs to the rootful `docker` group, and no rootless Podman/Docker runtime is installed. The HADES integration harness substitutes only the rootless-runtime predicate to exercise the route; a separate assertion confirms the real predicate rejects this host. `HADES_WORKSPACE_ENABLED` therefore defaults to `false`; do not grant the Hermes service rootful Docker socket access. Candidate/model quality, edits/tests/Git workflow, long tasks, production identity, and owner dogfood remain open.
- Natural workspace-intent follow-up fixed a user-facing miss from the initial candidate: “Why is this Python test failing?”, “Explain this function,” and “Can you read the config and tell me what it does?” now activate the bounded workspace route. Casual “test” mentions, an unrelated test-result question, and “workspace design patterns” remain model-first. These classifier cases run as part of the Hermes route test; this does not establish general language understanding or owner preference.
- Replayed eight selected conversation scenarios from the 50-case seed corpus, three times each, through persistent PLAIN/HADES Hermes 0.21.5 gateways on the same local Ollama 0.35.1/Qwen3.6 35B digest, with matching 4,096-token context and alternating order. Across 48 user turns per stack, median total latency was 1.46 s PLAIN / 1.43 s HADES, with 48 / 45 provider generations and 36,877 / 36,039 prompt tokens. HADES used its bounded canonical Grocy-unavailable response for three pantry turns (about 40 ms, no generation); it did not pretend to read pantry data. No owner preference was assigned. The replay exposed routing friction: after the user interrupted pantry work with “Explain this traceback first,” the disabled workspace route returned a canned workspace refusal instead of asking for the missing traceback. General code explanation/failure-diagnosis requests now stay model-first while workspace is disabled. Explicit file/path actions and terse action continuations grounded in code history remain gated, so the model cannot claim a file edit it did not perform. The replay then matched the PLAIN behavior by asking for the traceback. Focused runtime checks passed for the fallback and action gate, as well as the configured workspace boundary. See the [before](../benchmarks/hades-core-owner-conversation-v1.json) and [after](../benchmarks/hades-core-owner-conversation-v2.json) captures. Rootless workspace execution remains unqualified and disabled on this host.
- Agent Zero responsibility comparison against Hermes 0.21.5 source: HADES' optional `agent_zero_delegate` MCP adapter sends one bounded text task to Agent Zero's `/api/api_message`; input is capped at 2,000 characters, response at 4,000, and default timeout at 15 seconds. A lexical deny pattern plus a subordinate prompt rejects common infrastructure/write/secret terms, but does not create a technical read-only sandbox for the delegated task. Hermes' native `computer_use` is a desktop I/O capability, with session-scoped approvals and hard blocks for selected key combinations / dangerous typed shell patterns; it is not the same generic delegation API. Hermes also has subagent/worktree primitives, but HADES has not qualified their gateway exposure, workspace boundary, or effects. Its CUA `--yolo`/approval-bypass path escalates the driver to unrestricted permissions, so it is not an acceptable substitute under HADES bounds. **Decision: HOLD Agent Zero replacement/deletion; keep it disabled and private.** Reassess only after testing a concrete owner task against Hermes native subagent/workspace and bounded desktop paths, and do not describe the current regex-filtered delegation as a technical read-only guarantee.
- New local matched direct-agent comparison (`benchmarks/hades-core-local-agent-ordinary-pair-v1.json`): three warm synthetic greeting pairs using the same Hermes 0.21.5 agent constructor, staged Ollama 0.35.1, Qwen 3.6 35B Q4_K_M candidate digest, RTX 3080 Ti laptop, and disabled reasoning. HADES reduced prompt from 2,050 to 572 tokens (72.1%) and removed 19 schemas / 35,631 bytes, but median TTFT was 2,144 ms vs PLAIN 1,747 ms. Median total was 2,288 ms HADES vs 2,336 ms PLAIN, while HADES replies were much shorter (median 9 vs 34 output tokens). PLAIN is therefore slightly preferable on this greeting sample for faster visible response and fuller natural conversation; this is not Scotty preference evidence. Both TTFT medians are near/over target (HADES misses 2s; PLAIN meets narrowly). Staged model digest and hardware differ from the live production endpoint; direct AIAgent construction omits the frontend, gateway, MCP/Hindsight/domain services and owner data. Reduce the remaining HADES prefill/routing tax and verify response naturalness before claiming a usability improvement.
- The persistent-process follow-up (`benchmarks/hades-core-local-persistent-ordinary-probe-v1.json`) reduces per-turn process churn: one Hermes process created four AIAgents per stack. On turns 2–4, HADES median TTFT was 96 ms / wall 181 ms vs PLAIN 227 ms / wall 606 ms, while HADES prompt context stayed 572 tokens and PLAIN 2,050. The first requests were 2.1 s HADES and 5.3 s PLAIN, but the stack order was not balanced and the HADES request came second after model/prompt activity. Treat both cold-first and warm-repeat as exploratory; warm identical greetings are a favorable prefix-cache case. Warm HADES wording was often curt, including “Functioning normally.” A synthetic HADES-only style probe found a 31-token conversation instruction avoided system-capacity/status replies in four more greetings, with three sounding conversational and one still task-oriented. The overlay now applies a short generic-person version only when no classified memory, Grocy/household, web, homelab, finance, operator, control, or workspace intent is active. One direct replay with the committed wording used 606 prompt tokens, exposed zero tools, and answered “Good. How can I help?” Runtime contract coverage confirms it appears on a following ordinary greeting after workspace cleanup. This is still limited synthetic wording evidence, not owner preference.
- Ollama's current stable is available in an isolated staged runtime, but the tag pull yielded a different manifest digest from the deployed model. Same name, byte count and quantization do not prove identical weights. Preserve this as a fairness limitation.
- Production source provenance is incomplete. Live Open WebUI version is verified; Hermes version, active overlay, source SHA and actual per-request model route are unknown from this session. No authenticated owner chats were read.
- A disposable Open WebUI 0.11.4 candidate + Hermes 0.21.5 synthetic-provider trace checked the title path through the OpenAI-compatible gateway ([endpoint capture](../benchmarks/openwebui-hermes-title-composition-probe-v1.json)). One direct `/api/chat/completions` request produced one streamed answer request and one Hermes structured title request. Explicitly calling Open WebUI's separate `/api/v1/tasks/title/completions` endpoint then produced another streamed generation and another Hermes structured title request. With Hermes `model_upgrade_enabled: false`, that explicit task endpoint still returned a title, while the test client persisted it by sending the full chat object through the chat API; Hermes made no structured title calls. This proved endpoint composition only. A subsequent authenticated Chromium flow ([browser capture](../benchmarks/openwebui-hermes-browser-metadata-overhead-v1.json)) confirmed the frontend requests title, follow-up, and tag tasks after a normal chat. In one synthetic turn those requests plus the chat caused four streamed generations; Hermes title upgrades added four more structured generations. The visible and persisted answer was correct, but the persisted chat title stayed derived from the user prompt, and no follow-up/tag result appeared in the captured conversation. Disabling the three Open WebUI metadata tasks and Hermes title upgrade reduced the flow to one user generation while preserving the answer. This is a staging candidate, not production acceptance: no real model or owner was used, task quality is unproven, and deployed settings remain UNKNOWN. The HADES task-notification endpoint returned HTTP 503 because this fixture omitted the feed configuration; it polls at page load and every 30 seconds, while production compose requires the URL and key. This is not a per-message cost or a production failure signal. No production setting changed.
- Source pin gaps need explicit repair in a later maintenance slice: n8n external image, Ollama runtime, PaddleOCR transitive package, Agent Zero image-to-release mapping, and Actual adapter revision.
